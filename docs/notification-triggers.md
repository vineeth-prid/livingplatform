# Notification triggers — what fires, and who receives it

Generated by reading `EVENT_MAP` and `contextFor()` in
`apps/api/src/modules/notifications/core/notification-router.service.ts`, plus
the engines that dispatch directly. Current as of `be23979` + the auto-assign
work.

## How a notification is decided

```
domain event  →  EVENT_MAP binding  →  community preference (enabled? channels?)
              →  contextFor(): who + what variables
              →  RecipientResolver: channel address for that person
              →  template render  →  queue  →  worker  →  provider
```

Four places it can stop, all of them silent by design:

1. **No `EVENT_MAP` binding** — the event is not a notification.
2. **Preference disabled**, or every channel switched off for that event.
3. **`contextFor()` returns null** — nothing to say, or nobody to say it to.
   Most commonly the record has no resident attached.
4. **No channel address** — resident has no mobile, or the number will not
   parse to E.164; staff/vendor has no phone; recipient has no login account
   (in-app and push address a user id, not an inbox).

A delivery row exists from step 5 onward. **No row at all means it stopped at
1–4**; a row stuck in `QUEUED`/`PROCESSING` means it reached the worker.

## Resident-facing

| Trigger | Who receives it | Template |
| --- | --- | --- |
| Ticket raised | The ticket's resident — whoever raised it, or the unit's primary occupant when an admin raised it for them | `ticket-created` |
| Ticket status changed | Same | `ticket-updated` |
| Service request completed | The request's resident | `generic` |
| Booking confirmed | The booking's resident | `booking-confirmed` |
| Payment succeeded | The paying resident | `payment-success` |
| Maintenance due | Each invoice's resident, one message each, sent by the billing scheduler rather than the generation event | `maintenance-due` |
| Visitor pass created | The hosting resident | `visitor-pass` |
| Visitor approved | The hosting resident | `visitor-approved` |
| Resident created | The new resident (their login details) | `welcome` |
| Gate entry arrived | The unit's occupant — PRIMARY/OWNER first | `gate-entry-arrived` |
| OTP requested | The requesting user | `otp-requested` |

## Workforce-facing

| Trigger | Who receives it | Template |
| --- | --- | --- |
| Ticket assigned | The assignee — staff or vendor, whichever is set | `ticket-assigned` |
| Service request assigned | The assignee | `service-assigned` |
| Work order assigned | The assignee | `work-order-assigned` |
| Work order completed | The assignee (work orders are internal; there is no resident on them) | `work-order-completed` |

Assignment notifications fire for **auto-assignment too** — the same
`*.assigned` event is published whether a person or the rule made the choice.

## Admin/approver-facing

| Trigger | Who receives it | Template |
| --- | --- | --- |
| Visitor created (pending) | Every ACTIVE user in the community holding `visitor:approve`, capped at 25 | `visitor-pending` |
| Gate entry decided | The gate desk | per gate settings |

Approvers are resolved from **role grants**, not a hardcoded role key, so a
custom role holding `visitor:approve` is alerted too.

## Channel selection

Per community, per event, in `CommunityNotificationPreference`:

- **email** — defaults ON
- **whatsapp** — defaults OFF; must be switched on per event
- **in-app / push** — gate events only, where in-app is always on because the
  popup is the entire point of the feature

A per-event row overrides the community-wide `CommunitySettings` flags.

## Deliberately NOT notified

- **Ticket/service comments** — no notification exists.
- **Ticket closed** — `ticket-closed.hbs` exists but nothing sends it.
- **Work order created** — `work-order-created.hbs` exists but is unbound;
  only assignment and completion notify.
- **Service request created** — the resident just made it; only assignment and
  completion tell them anything new.
- **Announcements** are bound to `ANNOUNCEMENT` but publish to the community
  rather than an individual.

Templates existing without a binding is normal — they were written ahead of the
events. An unbound template sends nothing.
