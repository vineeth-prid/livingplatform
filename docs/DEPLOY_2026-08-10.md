# Deployment guide — 2026-08-10

Covers everything committed since the [2026-08-06 runbook](UPGRADE_2026-08-06.md)
(21 commits, `fa2acea..HEAD`) plus today's security fix.

**Target assumed by this guide:** a live stack whose database holds only demo /
test data. That removes the delicate parts of the 08-06 runbook — the duplicate
mobile-account merge and the vendor-coverage eyeball are data-quality steps that
only matter with real residents. They are listed at the end as *skipped, and why*.

---

## 0. Two things will stop the API from booting

Read this section even if you skip the rest.

### 0a. `docker-compose.production.yml` never passed the production secrets

`docker-compose.production.yml:85` sets `NODE_ENV: production`, and the compose
file has **no `env_file:` directive** — so only the variables named in its
`environment:` block reach the container. `APP_ENCRYPTION_KEY` was not in that
block. `--env-file .env.production` does *not* inject variables into containers;
it only fills `${...}` placeholders when compose parses the YAML.

Net effect: `APP_ENCRYPTION_KEY` arrived as `''`, and it is required at
`NODE_ENV=production` (`apps/api/src/config/env.validation.ts:136-141`, min 32
chars). **This deploy would have failed at boot** — and it predates today's work.

Fixed in this change: the compose `environment:` block now passes
`APP_ENCRYPTION_KEY`, `AUTH_DEFAULT_PASSWORD` and the three optional `VAPID_*`
vars. You must still define them in `.env.production`.

### 0b. `AUTH_DEFAULT_PASSWORD` is now enforced in production

Today's security fix. `validateEnv` throws if `NODE_ENV=production` and
`AUTH_DEFAULT_PASSWORD` is still the documented default `Living@123`
(`apps/api/src/config/env.validation.ts:478-487`). The fallback is published in
this repo, so every provisioned resident, staff and vendor account would
otherwise be claimable by whoever signs in first.

Set it. Boot fails loudly with the reason if you don't.

### What to add to `.env.production`

```bash
openssl rand -base64 48          # → APP_ENCRYPTION_KEY
openssl rand -base64 18          # → AUTH_DEFAULT_PASSWORD (min 8 chars)
npx web-push generate-vapid-keys # → VAPID_PUBLIC_KEY / VAPID_PRIVATE_KEY
```

```ini
APP_ENCRYPTION_KEY=<48-byte base64>
AUTH_DEFAULT_PASSWORD=<not Living@123>
VAPID_PUBLIC_KEY=<new>
VAPID_PRIVATE_KEY=<new>
VAPID_SUBJECT=mailto:ops@yourdomain
```

> **`APP_ENCRYPTION_KEY` is not rotatable in place.** It decrypts stored Razorpay
> keys, webhook secrets and WhatsApp API keys. Change it later and every stored
> secret becomes unreadable and must be re-entered by hand. Back it up wherever
> you keep the DB password.

> **Rotate the VAPID pair.** The previous keys were pasted into a chat transcript
> on 2026-08-04 — treat them as disclosed. Rotating invalidates existing push
> subscriptions; residents re-subscribe on next app open, which is fine here.

## 2. Migrations — 4 new, all automatic

`prisma migrate deploy` runs automatically in the API container's start command
(`apps/api/Dockerfile:39`), so **you do not run migrations by hand.** New since
08-06:

| Migration | What it does | Risk |
| --- | --- | --- |
| `20260807000000_tenant_category_settings` | New table, two FKs | None — purely additive |
| `20260808000000_normalize_mobile_usernames` | `UPDATE users` — trims country codes off login usernames to the last 10 digits | Rewrites live logins; see below |
| `20260809000000_work_evidence_stage` | New enum + nullable `stage` column on two attachment tables | None — additive, existing rows stay `NULL` |
| `20260810000000_vendor_community_coverage_backfill` | `UPDATE vendors` — gives vendors with an *empty* `communityIds` coverage of all their tenant's communities | Low — skips any vendor already scoped |

Two of those four are data migrations, not schema migrations. Both are written
defensively: the username rewrite only fires where the 10-digit form is
unclaimed, and the vendor backfill only touches empty arrays. Neither deletes
anything.

**No schema drift** — `apps/api/prisma/schema.prisma` last changed at `45c5a3a`,
which shipped its migration. The four most recent commits (`fbb487e` one resident
per unit, `72ce4b9` multi-community login, `cead3cd`, `fc5127e`) are
application-layer only and need no migration.

## 3. Deploy

```bash
docker compose -f docker-compose.production.yml --env-file .env.production up -d --build
```

`--build` is required, not optional: the three frontends bake `VITE_API_BASE_URL`
in at image build time via build-args (`docker-compose.production.yml:129,136,143`).
A restart without a rebuild ships the old JS.

## 4. Reseed — the load-bearing step

```bash
docker compose -f docker-compose.production.yml exec -e SEED_SKIP_DEMO=true api \
  node node_modules/prisma/build/index.js db seed
```

The seed is the **only** thing that creates roles and permission grants — no
migration inserts a role (verified: zero `INSERT INTO "roles"` across all 29
migration files). Skip this and the SECURITY role and its gate/delivery
permissions do not exist, so gate access and staff work-order creation stay
broken no matter what code you deployed.

It is idempotent (upsert / find-or-create throughout), so re-running is safe.
One caveat: grants are an **authoritative sync** — `seed.ts:89-93` revokes any
`rolePermission` not in the current role definition. Always seed from the commit
you just deployed, never an older checkout.

On `SEED_SKIP_DEMO`: your DB holds demo data already, so either value works. With
the flag, you get reference data only. Without it, the seed re-creates the
`living-demo` tenant plus `admin@living.local` and `association@living.local` at
the repo-published password `Living!2024` — fine on a test box, never on a real
one. Given you'll eventually promote this environment, using the flag now is the
better habit.

## 5. SECURITY role backfill — manual, no script exists

Guards created **before** the SECURITY role existed hold no grant. There is no
script for this; it exists only as SQL in the 08-06 runbook. Dry run first:

```sql
SELECT s."userId", s."communityId" FROM staff s
WHERE upper(trim(s.role)) = 'SECURITY' AND s."deletedAt" IS NULL AND s."userId" IS NOT NULL;
```

Zero rows → nothing to do, skip. Otherwise:

```sql
INSERT INTO user_roles (id, "userId", "roleId", "communityId", "createdAt")
SELECT gen_random_uuid()::text, s."userId", r.id, s."communityId", now()
FROM staff s CROSS JOIN roles r
WHERE r.key = 'SECURITY' AND r."tenantId" IS NULL
  AND upper(trim(s.role)) = 'SECURITY' AND s."deletedAt" IS NULL AND s."userId" IS NOT NULL
ON CONFLICT ("userId", "roleId", "communityId") DO NOTHING;
```

Must run **after** the seed — it joins against the SECURITY role the seed
creates. Takes effect on each guard's next token refresh, not instantly.

## 6. Verify

```bash
curl -fsS https://api.<domain>/api/v1/health        # liveness → {status:ok}
curl -fsS https://api.<domain>/api/v1/health/ready  # db + redis + storage + heap
docker compose -f docker-compose.production.yml ps  # all healthy
```

Readiness checks four indicators (`health.controller.ts:37-47`). Note the
container healthcheck only hits **liveness**, so a container can report healthy
while Redis or storage is down — check `/ready` yourself.

Then, in the apps:

| Check | Why this one |
| --- | --- |
| Sign in as a community admin | Confirms the seed's grants took |
| Open Gate → log a delivery | The SECURITY role path from §4/§5 |
| Resident app → switch community | `72ce4b9` multi-community login, no migration to verify it |
| Staff work order → attach a before photo | `20260809000000_work_evidence_stage` + storage |
| Vendor list → confirm coverage is populated | `20260810000000_vendor_community_coverage_backfill` |
| Log in with a 10-digit mobile | `20260808000000_normalize_mobile_usernames` |

## 7. Deliberately skipped

| Step from the 08-06 runbook | Why it's skipped here |
| --- | --- |
| Merge duplicate country-code accounts | The migration leaves both rows where a person has two accounts. Only matters with real residents — on demo data, ignore. |
| Eyeball vendor `serviceCategories` before backfill | It drives auto-assignment. Worth care on real data; not on test data. |
| RLS activation | Staged but **inert** by design. Activating needs `DB_RLS_ENABLED=true` *and* `apps/api/prisma/rls/ACTIVATE.sql` (`FORCE ROW LEVEL SECURITY`) *and* a non-owner DB role. It is defence-in-depth; tenant isolation is application-level today. Do it as its own change, never bundled with a feature deploy. |

## 8. Post-deploy configuration

Not deployment steps — things only reachable through the UI once it's up.

- Per-community Razorpay credentials (Portal → Billing → Payment settings → **Test connection**). These are *not* env vars; they're stored encrypted with `APP_ENCRYPTION_KEY`.
- Register Razorpay webhooks: `…/payments/webhooks/razorpay/<communityId>/<PURPOSE>`.
- `BILLING_SWEEP_ENABLED` — leave on exactly one API replica if you scale out.
- WhatsApp pairing if `WHATSAPP_PROVIDER=openwa` (Portal → Platform admin → WhatsApp → scan QR).
