# Upgrade runbook — 2026-08-06 release

Covers everything merged between the last deployed build and `06a2a6e`: Gate
Management (Sprint 13), the SECURITY role, the 46-item defect sweep
(Sprints A–H), and the OpenWA `previewUrl` fix.

This is an **upgrade** runbook. For a first install, follow
[`DEPLOYMENT.md`](DEPLOYMENT.md) instead — it supersedes this document, and the
seed rules below still apply.

> **Read this first.** Several fixes in this release are inert until the seed
> runs. If you deploy the code and skip step 4, gate entries, staff work-order
> creation and everything security-related will still look broken, and you will
> reasonably conclude the fixes did not work.

---

## 0. What has actually been verified

Every change here is verified by tests, types, lint and builds only: **382 API
tests across 49 suites, 25 resident tests, lint clean on six workspaces, and
api / portal / resident / workforce all building.**

Nothing in this release has been run against a live database or a running
stack — no such environment existed while it was built. The migrations are
additive and reviewed, but **step 1 (the backup) is doing real work.** Treat
staging as mandatory, not optional.

## 2. New environment variables

Add to `.env.production` **before** rebuilding.

| Variable | Required? | Notes |
| --- | --- | --- |
| `VAPID_PUBLIC_KEY` | For push | Web Push (RFC 8292). Without it the push channel disables itself cleanly — no crash, no push. |
| `VAPID_PRIVATE_KEY` | For push | Treat as a secret. |
| `VAPID_SUBJECT` | For push | `mailto:you@example.com`. Defaults to `mailto:support@living.local`. |
| `SEED_SKIP_DEMO` | **Yes, on production** | `true`. See step 4 — this is the one that protects you. |

Generate a fresh VAPID pair on the server:

```bash
npx web-push generate-vapid-keys
```

> **Do not reuse the pair that was shared in chat during development.** It has
> been disclosed and must be treated as burned. Rotating VAPID keys invalidates
> existing push subscriptions — browsers simply re-subscribe on next visit, so
> the cost is one missed notification per device, not a broken deployment.

The resident app reads the public key **from the API at runtime**, so rotating
keys does not require a frontend rebuild.

Already required since Sprint 11, re-stated because boot fails without it in
production: `APP_ENCRYPTION_KEY`.

## 4. Reseed — this is load-bearing

**The single most important step in this runbook.** The seed is what creates the
SECURITY role and its permission grants. Skip it and the gate module has no role
to attach anyone to.

```bash
docker compose -f docker-compose.production.yml exec \
  -e SEED_SKIP_DEMO=true api \
  node node_modules/prisma/build/index.js db seed
```

`SEED_SKIP_DEMO=true` is **not optional on production.** Without it the seed also
upserts the demo tenant, demo community and its accounts — including logins with
a published default password — onto your live database. The flag stops after
reference data: permissions, roles, ticket categories, system services.

Reference-data seeding is idempotent and safe to re-run. Note that role grants
are **authoritative, not additive**: a permission removed from a role definition
is revoked on seed. That is intended, and it is why the seed must run after any
release that changes roles.

Expected output:

```
✓ N permissions
✓ N system roles + grants
✓ N system ticket categories
✓ N system services
• SEED_SKIP_DEMO=true — reference data only, no demo tenant
Done.
```

Confirm the role exists before moving on:

```sql
SELECT key, name FROM roles WHERE key = 'SECURITY' AND "tenantId" IS NULL;
```

One row, or stop here.

## 5. Backfill existing security guards

New staff whose job role is `SECURITY` get the role automatically. Staff created
**before** this release do not — nothing granted it at the time.

Dry run first:

```sql
SELECT s.id, s."firstName", s."lastName", s.role, s."communityId", s."userId"
FROM staff s
WHERE upper(trim(s.role)) = 'SECURITY'
  AND s."deletedAt" IS NULL
  AND s."userId" IS NOT NULL
  AND NOT EXISTS (
    SELECT 1 FROM user_roles ur
    JOIN roles r ON r.id = ur."roleId"
    WHERE ur."userId" = s."userId"
      AND ur."communityId" = s."communityId"
      AND r.key = 'SECURITY' AND r."tenantId" IS NULL
  );
```

Read the list. These people are about to gain access to the gate register, which
carries resident names, unit numbers and phone numbers — confirm every row is
genuinely a guard before granting.

```sql
INSERT INTO user_roles (id, "userId", "roleId", "communityId", "createdAt")
SELECT gen_random_uuid()::text, s."userId", r.id, s."communityId", now()
FROM staff s
CROSS JOIN roles r
WHERE r.key = 'SECURITY' AND r."tenantId" IS NULL
  AND upper(trim(s.role)) = 'SECURITY'
  AND s."deletedAt" IS NULL
  AND s."userId" IS NOT NULL
ON CONFLICT ("userId", "roleId", "communityId") DO NOTHING;
```

`ON CONFLICT DO NOTHING` makes this safe to re-run.

> Permissions are embedded in the JWT, so a backfilled guard gains access **on
> their next token refresh**, not instantly. If someone needs it immediately,
> have them sign out and back in.

### Vendor service categories

Auto-assignment routes work by vendor service category. Vendors created before
this release may have none, in which case they are simply skipped by
auto-assignment and remain manually assignable — degraded, not broken.

```sql
SELECT id, name, "serviceCategories" FROM vendors
WHERE "deletedAt" IS NULL AND coalesce(array_length("serviceCategories", 1), 0) = 0;
```

Fill these in through the portal rather than by hand — the UI validates against
the live catalog.

## 6. Smoke test

Fastest path to catching the failure modes this release actually has:

1. **Platform admin** → Communities → key icon on a row. The association admin's
   account loads; the temporary password is *not* shown (correct — it is a hash).
   Reset issues a new one, displayed once.
2. **Platform admin** → Payments. Per-community totals render, rail filters and
   search work.
3. **Community admin** → create a staff member with job role `SECURITY`. Confirm
   they can sign in and reach the gate screen.
4. **Security login** → record a delivery. **This is the regression that made the
   whole gate module look broken** — the register 400'd on every list call. It
   must save *and appear in the list*.
5. **Resident** → the delivery approval arrives. With the app open first, then
   fully closed (that path is push, and needs step 2).
6. **Resident** → open a ticket with a due date set by an admin; the resident now
   sees "Due today" / "Overdue by N days".
7. **Staff** → open a work order and start it. Confirm a *completed* work order
   offers no Start button.

## 7. Rollback

Migrations are additive, so the previous image runs against the new schema —
extra tables and nullable columns are ignored by older code. To roll back:

```bash
git checkout <previous-sha>
docker compose -f docker-compose.production.yml --env-file .env.production up -d --build
```

**Do not roll the schema back** to undo a bad deploy. Restore the step 1 dump
only if data is actually corrupt, and accept losing everything written since.

The reseed cannot be rolled back by re-running an older seed — role grants are
authoritative, so an older seed would revoke the new permissions. That is
recoverable by re-running the current seed; it is not recoverable if you have
also reverted the code that defines the roles.

## Known limitations shipping with this release

Honest list, so nothing here surprises you in testing:

- **RLS is staged but inert.** The tenant row-level-security backstop exists in
  the schema and does nothing until `FORCE ROW LEVEL SECURITY` is enabled. It is
  a defence-in-depth layer, not the tenant isolation currently in force — that
  remains application-level.
- **Reset password shows a disabled control** for staff and vendors with no
  linked login. That is the honest state, not a bug: provisioning links an
  existing account to the *first* profile using a phone number and leaves later
  ones unlinked.
- **Per-community revenue is now visible to the platform operator.** This
  reverses an earlier design decision. Totals only — no resident, unit or
  invoice detail crosses the tenant boundary.
- **Work-order approval Phases 2 and 3** (origin recommend buttons, AMC visit
  tracking, ticket sub-states) are deferred and not in this release.
- **OpenWA media sending is unvalidated.** `06a2a6e` fixed `send-text`, which was
  400ing on every message because OpenWA's DTO uses `forbidNonWhitelisted` and
  rejected the extra `previewUrl` property. The sibling senders have the same
  failure mode and have **not** been tested against a live gateway:
  `sendMedia` passes `url`/`base64`/`caption`/`filename`/`type`, and
  `sendLocation`/`sendButtons` spread arbitrary objects straight into the
  payload. `sendMedia` is reachable from the notification engine
  (`whatsapp.channel.ts:65`) whenever a notification carries media, so this is a
  live path, not dead interface surface. Validate each against its DTO in the
  gateway's `openapi.json` before relying on media notifications. Text-only
  WhatsApp is unaffected.
